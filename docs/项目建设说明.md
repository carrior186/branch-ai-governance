# 项目建设说明

> 项目：光华管理学院本科生党支部 AI 协作规范与实践体系  
> 仓库暂名：`branch-ai-governance`  
> 当前阶段：内容填充第一阶段  
> 本说明描述建设方案，不赋予讨论材料正式制度效力。

## 一、建设目标

本项目希望把零散的 AI 使用经验转化为一套可维护、可检索、可实践验证的协作体系，同时保留未来公开推广的可能性。它承担三项功能：

1. **规范与指导**：明确共同原则、责任边界和领域方法。
2. **知识积累**：把经验证、经脱敏、经审核的工作流和案例沉淀为可复用知识。
3. **Agent 协作**：通过统一 Skill 帮助使用者找到依据、澄清需求、设计流程并设置人工验收点。

建设目标不是让 AI 代替支部职责，也不是建立真实工作资料库。项目是否成功，应以“能否帮助成员安全、清楚、可复核地完成工作”为标准，而不是以文件数量或自动化程度衡量。

## 二、设计原则

| 原则 | 建设含义 |
|---|---|
| 上位规范统一 | 五个分则遵循总则，不降低共同的责任和信息安全要求 |
| 内容模块化 | 总则、分则、案例和 Skill 各自承担不同功能 |
| 单一权威来源 | 同一规则只在一个正式位置维护，其他内容通过链接引用 |
| 人工最终负责 | AI 可以辅助起草、检查和维护，责任主体批准关键成果和重大修改 |
| 持续迭代 | 从小范围实践获取反馈，成熟后再扩展，不一次性追求完整 |
| 可公开设计 | 从一开始排除真实工作资料和个人信息，降低未来公开时的清理风险 |
| 最小化工程 | 没有真实需求和成熟内容时，不建立空目录、复杂脚本或重复 Skill |

## 三、内容架构

### 1. 总则

总则保存所有领域共同适用的原则、边界和治理方法，由副书记牵头维护。当前已形成 v0.1 完整讨论稿，以七章结构提供共同方法和待审议文本；“完整”不代表已经通过，正式化前仍需逐项审议并核验外部依据。

### 2. 领域指南

分则按实际岗位和任务组织：

| 领域 | 主要责任角色 | 重点 |
|---|---|---|
| 支部管理 | 书记、副书记 | 整体规划、分工、会议与跨领域协调 |
| 组织工作 | 组织委员 | 组织生活、流程清单、公开依据和非敏感材料方法 |
| 宣传工作 | 宣传委员 | 文案、视觉、发布审核、版权与对外口径 |
| 纪检工作 | 纪检委员 | 纪律教育、通用风险提示和规范一致性检查 |
| 活动统筹 | 活动组织者 | 策划、排程、分工、物资、现场与复盘 |

交叉任务不必被强行归入单一领域。应确定一个主要责任领域，并组合引用其他分则；最终审核责任随事项性质归属相应负责人。

### 3. 案例

案例用于说明如何应用规范，不是新的规范来源。只有同时满足以下条件时才新增案例文件：

- 对今后的相似任务确有复用价值；
- 已移除真实姓名、身份、联系方式、组织关系、内部安排等信息；
- 不会因时间、地点、角色等组合线索重新识别相关人员或事项；
- 已核验事实、版权和对外公开边界；
- 已由相应领域负责人审核。

当前没有合格案例，因此不创建空的 `cases/` 目录。首个案例获批时再建立该目录和最小索引。

### 4. Skill 入口

`branch-assistant` 是统一入口。它读取总则和一个或多个相关分则，引导任务识别、需求澄清、人机分工、流程设计、分阶段执行与人工验收。它不保存真实资料、不创造政策，也不取代任何负责人。

初期不按五个领域拆成五个 Skill。只有在使用量、领域差异和维护成本证明拆分有价值时，再审议是否调整。

## 五、信息分类与公开边界

### 可进入拟公开仓库的内容

- 经审核的通用原则和领域方法；
- 使用虚构信息编写的模板；
- 已完成脱敏、核验和公开审查的案例；
- Skill 指令、项目维护说明和变更记录；
- 已经公开且允许引用的外部依据链接或简短说明。

### 不进入仓库的内容

- 党员、申请人、联系人、活动参与者等个人信息；
- 组织关系、评价意见、谈话记录、举报线索、纪律个案等材料；
- 内部会议原始内容、未公开安排、详细行程、安全方案和权限信息；
- 账号、密钥、内部链接、访问令牌或系统配置；
- 未确认版权、授权或公开范围的图片、音视频和文档；
- 其他依据现行规定不适合公开或外部处理的信息。

本地仓库也按未来公开标准管理，因为 Git 历史、备份或后续权限变化都可能扩大信息传播范围。发现敏感信息时应停止传播并按实际管理要求处置；不能仅通过普通删除假定历史记录已经清除。

## 六、治理与维护机制

### 角色分工

- **书记**：审定整体方向及重大治理事项。
- **副书记**：牵头总则维护、跨领域协调、版本组织和一致性检查。
- **组织委员、宣传委员、纪检委员**：分别维护对应领域指南并审核相关实践内容。
- **活动组织者**：提出和验证活动统筹方法，由具体活动指定负责人归口审核。
- **其他参与者**：可提交问题、建议和脱敏实践反馈，不因此获得批准权限。
- **AI Agent**：辅助起草、比较、检查、检索和整理，不承担批准与最终责任。

### 变更分类

以下变化视为重大变更：

- 新增或改变基本原则、责任主体、强制步骤或禁止事项；
- 调整敏感信息边界、对外公开范围或批准机制；
- 把讨论稿标记为正式版本；
- 新增外部系统、自动化发布或数据处理流程；
- 解决总则与分则之间的实质冲突。

重大变更应由副书记组织影响检查，由相关领域负责人审核，并由书记或既定批准主体确认。文字修正、链接维护和不改变含义的排版调整可采用简化审核，但仍应确保不引入事实变化。

### 建议修改流程

1. 提出问题和修改目的，不在提案中放入真实工作资料。
2. 确定唯一需要修改的权威文件和受影响的引用文件。
3. 由 AI 或人员形成草稿，明确“新增、修改、删除”的实际影响。
4. 对照总则、相关分则和信息边界进行检查。
5. 由责任人审核；重大变更完成额外批准。
6. 更新变更记录，合并后在真实但不含敏感数据的场景中验证。
7. 根据反馈修订，避免把一次成功经验直接推广为普遍规则。

## 七、从讨论框架到正式规范

建议分阶段推进：

### 阶段 1：确认框架

由书记、副书记和领域负责人确认项目定位、五个分则边界、信息分类、维护责任和正式批准方式。此阶段不追求详细条文。

### 阶段 2：形成总则讨论稿

当前已形成 v0.1 完整讨论稿，补充了适用情境、责任主体、执行流程、人工检查点和代表性提示词。下一步是逐项审议总则附录中的政策问题；需要引用外部规定时，由人工核验有效版本。

### 阶段 3：选择一个低风险领域试点

建议从只使用公开或虚构信息的任务开始，例如公开活动文案的结构检查或虚构活动方案的流程设计。记录 Skill 是否找到正确文件、是否提出有效问题、是否清楚设置人工检查点。

### 阶段 4：完善分则与首批案例

仅把多次验证、能够脱敏且具有复用价值的方法写入分则或案例。案例必须通过公开审查。

### 阶段 5：审议正式版本与公开发布

完成跨文件一致性、信息安全、版权、链接和仓库历史检查；明确版本号、批准主体、生效日期和复审周期后，再决定是否对外公开。

## 八、验证与质量标准

每次重要迭代至少检查：

- **定位**：是否仍是规范与方法项目，而非真实资料库？
- **效力**：讨论、建议和正式要求是否清楚区分？
- **一致性**：分则是否遵循总则，Skill 是否只应用而不创造规则？
- **责任**：是否能看出谁维护、谁核验、谁批准？
- **安全**：是否包含直接或可组合识别的敏感信息？
- **可用性**：一名新使用者能否找到相关依据并知道下一步？
- **最小化**：新增文件或自动化是否解决了真实、重复出现的问题？

可以用下列观察指标评估试点，但不宜机械追求数字：找到正确规范所需时间、人工发现的事实或流程错误、未解决问题是否被清楚升级、使用者对责任边界的理解，以及实践反馈转化为可复用方法的比例。

## 九、本地使用方式

在 Codex 中打开仓库根目录后，可以直接提出：

> 使用 `branch-assistant`，按照本项目现有规范，帮助我设计一项只使用公开或虚构信息的主题党日活动筹备流程。

Agent 应先读取总则 v0.1，再组合活动统筹与任务涉及的其他分则。当前分则仍是轻量占位，因此输出应包含待负责人确认的问题，而不能声称已经遵循一套完整正式制度。

维护者修改文件前应先阅读根目录 `AGENTS.md`。任何真实任务资料应保存在经组织确认的合适系统中，不要为了让 Skill 读取而复制进仓库。

## 十、Git 与后续 GitHub 发布

当前首先建立本地 Git 仓库，不假定已获得 GitHub 组织、账号或目标仓库的创建权限。建议在正式公开前完成一次人工仓库审查，并由有权限的维护者执行发布。

后续步骤：

1. 在 GitHub 上创建空仓库 `branch-ai-governance`，不要自动添加 README、许可证或其他初始文件。
2. 确认公开或私有属性、仓库归属、管理员、维护者和分支保护要求。
3. 在本地添加远程地址并核对目标，避免推送到个人或错误组织仓库。
4. 再次检查当前文件、完整 Git 历史、作者信息、链接、版权和敏感内容。
5. 首次推送后，在 GitHub 页面复核可见内容与权限设置。

示例命令中的地址必须替换为人工确认的真实地址：

```bash
git remote add origin <经确认的远程仓库地址>
git remote -v
git push -u origin main
```

是否采用开源许可证、贡献者协议、Issue 模板或自动化检查，应在公开范围和协作模式明确后决定；当前不为未来可能的需求预建文件。
